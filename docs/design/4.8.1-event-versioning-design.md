# 4.8.1 — Event Versioning Design

> Design-only phase. No code. Produces specification for 4.8.2 (Infrastructure) and 4.8.3 (Migration).

---

## 1. Problem Statement

The current event system has `metadata.version: number` but:
- All events are version 1 (hardcoded in `createEvent`)
- No mechanism to evolve event payloads without breaking consumers
- No upcasting from old versions to new versions
- No compatibility matrix between producers and consumers
- Event Store has no version tracking per event type

As the platform grows and new products are added, event schemas will evolve. Without versioning, we risk:
- Breaking subscribers when payloads change
- Losing data during replay of old events
- Inability to audit historical events

---

## 2. Event Envelope

Every event stored in the Event Store must be wrapped in an **envelope** that carries versioning metadata.

### Current Structure

```typescript
interface DomainEvent {
  eventId: string;
  eventType: string;
  aggregateId: string;
  aggregateType: string;
  payload: Record<string, unknown>;
  metadata: EventMetadata;
  occurredAt: string;
}
```

### Proposed Envelope

```typescript
interface EventEnvelope {
  // Identity
  eventId: string;
  eventType: string;
  eventTypeVersion: number;     // NEW: schema version of this event type
  aggregateId: string;
  aggregateType: string;

  // Payload
  payload: Record<string, unknown>;

  // Metadata
  metadata: EventMetadata;

  // Temporal
  occurredAt: string;
  storedAt: string;             // NEW: when stored in Event Store

  // Schema
  schemaVersion: number;        // NEW: envelope schema version (currently 1)
}
```

### Fields

| Field | Type | Description |
|-------|------|-------------|
| `eventTypeVersion` | `number` | Schema version of this specific event type (e.g., `CheckoutCompleted` v1, v2) |
| `schemaVersion` | `number` | Envelope schema version (currently 1, increments if envelope structure changes) |
| `storedAt` | `string` | ISO timestamp when the event was persisted to the Event Store |

## 3. Event Metadata

### Current

```typescript
interface EventMetadata {
  readonly tenantId: string;
  readonly userId?: string;
  readonly correlationId?: string;
  readonly causationId?: string;
  readonly version: number;
  readonly source?: string;
}
```

### Proposed

```typescript
interface EventMetadata {
  readonly tenantId: string;
  readonly userId?: string;
  readonly correlationId?: string;
  readonly causationId?: string;
  readonly source?: string;

  // REMOVED: version (moved to envelope.eventTypeVersion)
}
```

**Rationale:** The `version` field in metadata is ambiguous — it's unclear if it refers to the envelope version, the event type version, or the schema version. Moving it to the envelope makes it explicit.

## 4. Event Type Versioning

### Rules

1. **Each event type has its own version number** — independent of other event types
2. **Version starts at 1** — `CheckoutCompleted` v1, `AppointmentCreated` v1, etc.
3. **Version increments when payload changes** — adding required fields, removing fields, changing types
4. **Adding optional fields** does NOT require a version bump (backward compatible)
5. **Removing required fields** or **changing types** requires a version bump (breaking change)

### Version Increment Rules

| Change | Version Bump? | Example |
|--------|---------------|---------|
| Add optional field | ❌ No | `clientId?: string` added to `CheckoutCompleted` |
| Add required field | ✅ Yes | `tenantId: string` added to payload |
| Remove field | ✅ Yes | `hasClubCredit` removed |
| Change field type | ✅ Yes | `total: number` → `total: string` |
| Rename field | ✅ Yes | `staffId` → `professionalId` |
| Change enum values | ✅ Yes | `paymentStatus: 'paid' \| 'pending'` → adds `'partial'` |

### Current Event Versions

| Event Type | Current Version | Notes |
|------------|----------------|-------|
| `CheckoutCompleted` | v1 | |
| `CheckoutReverted` | v1 | Prepared, not published |
| `AppointmentCreated` | v1 | |
| `AppointmentCancelled` | v1 | |
| `AppointmentCompleted` | v1 | Prepared, not published |
| `CashClosingCompleted` | v1 | |
| `SubscriptionCreated` | v1 | |
| `SubscriptionCancelled` | v1 | |
| `CreditsDeducted` | v1 | |
| `TransactionCreated` | v1 | Prepared, not published |
| `CommissionCalculated` | v1 | Prepared, not published |

## 5. Compatibility Matrix

### Producer-Consumer Contract

Each subscriber declares which versions it can handle:

```typescript
interface EventConsumer {
  eventType: string;
  canHandle: {
    fromVersion: number;  // minimum version this consumer supports
    toVersion: number;    // maximum version this consumer supports
  };
}
```

### Example

```typescript
const analyticsSubscriber: EventConsumer = {
  eventType: 'CheckoutCompleted',
  canHandle: { fromVersion: 1, toVersion: 2 },
};
```

This means:
- Can handle `CheckoutCompleted` v1 and v2
- Cannot handle v3+ (would need upcasting or update)

### Compatibility Rules

| Scenario | Action |
|----------|--------|
| Consumer handles event version within range | Process normally |
| Consumer handles event version below range | Upcast event to latest supported version |
| Consumer handles event version above range | Skip event (log warning) |
| No consumer registered | Skip event (log warning) |

## 6. Upcasters

### Purpose

Transform events from older versions to the latest version. This allows consumers to always work with the latest schema, even when processing historical events.

### Interface

```typescript
interface EventUpcaster {
  /** The event type this upcaster handles */
  eventType: string;

  /** The version this upcaster transforms FROM */
  fromVersion: number;

  /** The version this upcaster transforms TO */
  toVersion: number;

  /** Check if this upcaster can handle the event */
  canHandle(event: EventEnvelope): boolean;

  /** Transform the event from fromVersion to toVersion */
  upcast(event: EventEnvelope): EventEnvelope;
}
```

### Example

```typescript
// CheckoutCompleted v1 → v2
// v2 adds `taxAmount` field (optional, defaults to 0)
const CheckoutCompletedV1ToV2: EventUpcaster = {
  eventType: 'CheckoutCompleted',
  fromVersion: 1,
  toVersion: 2,
  canHandle: (event) =>
    event.eventType === 'CheckoutCompleted' && event.eventTypeVersion === 1,
  upcast: (event) => ({
    ...event,
    eventTypeVersion: 2,
    payload: {
      ...event.payload,
      taxAmount: 0,  // default value for new field
    },
  }),
};
```

### Registry

```typescript
interface UpcasterRegistry {
  register(upcaster: EventUpcaster): void;
  getUpcasters(eventType: string): EventUpcaster[];
  upcastToLatest(event: EventEnvelope): EventEnvelope;
}
```

### Chaining

Multiple upcasters can be chained:

```text
v1 → v2 → v3 (latest)
```

The registry finds the chain: `[V1ToV2, V2ToV3]` and applies them in order.

## 7. Replay with Versioning

### Current Replay Flow

```text
EventStore → ReplayEngine → EventBus → Subscribers
```

### Proposed Replay Flow

```text
EventStore → ReplayEngine → UpcasterRegistry → EventBus → Subscribers
```

The Replay Engine applies upcasting before publishing to the EventBus. This ensures:
- Subscribers always receive events in their latest schema
- Historical events are transparently upgraded
- No subscriber needs to handle multiple versions

### Replay Options (Extended)

```typescript
interface ReplayOptions {
  // Existing options...
  eventType?: string;
  aggregateType?: string;
  aggregateId?: string;
  tenantId?: string;
  from?: string;
  to?: string;
  dryRun?: boolean;
  batchSize?: number;
  continueOnError?: boolean;
  onProgress?: (progress: ReplayProgress) => void;

  // NEW options
  upcast?: boolean;           // Apply upcasting before replay (default: true)
  targetVersion?: number;     // Upcast to specific version (default: latest)
}
```

## 8. Snapshot Strategy

### Purpose

Avoid replaying all events from the beginning of time. Snapshots capture aggregate state at a point in time.

### Design

```typescript
interface AggregateSnapshot {
  aggregateId: string;
  aggregateType: string;
  tenantId: string;
  version: number;              // Event version at time of snapshot
  lastEventId: string;          // Last event processed
  lastEventAt: string;          // Timestamp of last event
  state: Record<string, unknown>; // Serialized aggregate state
  createdAt: string;
}
```

### When to Snapshot

- After every N events (e.g., every 100 events)
- After critical events (e.g., `CheckoutCompleted`)
- On demand (manual snapshot)

### Replay with Snapshots

```text
1. Load latest snapshot for aggregate
2. Replay events after snapshot's lastEventId
3. Apply events to snapshot state
4. (Optional) Create new snapshot
```

### Table Schema

```sql
CREATE TABLE aggregate_snapshots (
  id TEXT PRIMARY KEY DEFAULT gen_random_uuid()::text,
  aggregate_id TEXT NOT NULL,
  aggregate_type TEXT NOT NULL,
  tenant_id TEXT NOT NULL,
  version INTEGER NOT NULL,
  last_event_id TEXT NOT NULL,
  last_event_at TIMESTAMPTZ NOT NULL,
  state JSONB NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_snapshots_aggregate ON aggregate_snapshots(aggregate_type, aggregate_id);
CREATE INDEX idx_snapshots_tenant ON aggregate_snapshots(tenant_id);
```

## 9. Event Store Schema Changes

### Current `event_store` Table

```sql
CREATE TABLE event_store (
  id TEXT PRIMARY KEY,
  event_id TEXT UNIQUE NOT NULL,
  event_type TEXT NOT NULL,
  aggregate_id TEXT NOT NULL,
  aggregate_type TEXT NOT NULL,
  payload JSONB NOT NULL,
  metadata JSONB NOT NULL,
  occurred_at TIMESTAMPTZ NOT NULL,
  stored_at TIMESTAMPTZ DEFAULT now(),
  source TEXT
);
```

### Proposed Changes

```sql
-- Add version columns
ALTER TABLE event_store ADD COLUMN event_type_version INTEGER NOT NULL DEFAULT 1;
ALTER TABLE event_store ADD COLUMN schema_version INTEGER NOT NULL DEFAULT 1;

-- Index for version queries
CREATE INDEX idx_event_store_version ON event_store(event_type, event_type_version);
```

## 10. Migration Strategy (4.8.3 Preview)

### Phase 1: Infrastructure (4.8.2)

- Create `EventEnvelope` interface
- Create `EventSerializer` (serialize/deserialize with version)
- Create `EventRegistry` (register event types with versions)
- Create `UpcasterRegistry` (register and chain upcasters)
- Update `ReplayEngine` to support upcasting
- Update Event Store schema

### Phase 2: Current Events (4.8.3)

- All current events remain at v1
- No upcasters needed yet (all v1)
- Update `createEvent` to include `eventTypeVersion`
- Update all event publishers to use new envelope

### Phase 3: First Version Bump (Future)

- When `CheckoutCompleted` evolves to v2:
  - Create `CheckoutCompletedV1ToV2` upcaster
  - Update `CheckoutCompletedEvent` type to v2
  - Register upcaster in `UpcasterRegistry`
  - Subscribers continue working unchanged

## 11. Compatibility Guarantees

### For Producers

- Always publish events at the latest version
- Never publish events at older versions
- Use `createEvent` which auto-sets `eventTypeVersion`

### For Consumers

- Declare `canHandle: { fromVersion, toVersion }`
- Always code against the latest version schema
- Upcasting is handled transparently by the registry

### For Event Store

- Events are stored with their original version (never modified)
- Upcasting happens at read time, not write time
- Historical events are preserved exactly as stored

## 12. Decision Log

| Decision | Rationale |
|----------|-----------|
| Envelope pattern | Separates event data from versioning metadata |
| Per-event-type versioning | Independent evolution of different event types |
| Upcasting at read time | Preserves original events, transforms on demand |
| Chain upcasters | Support multi-step version upgrades (v1→v2→v3) |
| Snapshots optional | Not needed at current scale, but designed for future |
| Schema version on envelope | Allows envelope structure to evolve independently |
| `storedAt` field | Distinguishes when event occurred vs when it was stored |
