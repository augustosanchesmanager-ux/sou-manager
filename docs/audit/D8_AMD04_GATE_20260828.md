## 1. O que foi implementado (fechamento do lifecycle)

Fecha o gap: item `failed` sem caminho server-side de recuperação.

```text
processing
   ├── success → published
   └── failure → handle_processing_failure
                     ├── retry (backoff) → pending → re-claimable
                     └── dead_letter (após retry_max_attempts)
processing órfão (>5min) → recover_stale_processing → pending
```

| Entregável | Arquivo |
|-----------|---------|
| `handle_processing_failure(item, tenant, error)` — NOVO RPC | `supabase/migrations/20260828000000_d8_worker_retry_dead_letter.sql` |
| `recover_stale_processing(tenant)` — NOVO RPC | 〃 |
| **Amenda** `claim_next_outbox_item` predica `(retry_next_retry_at IS NULL OR <= now())` | 〃 |
| Worker usa `handle_processing_failure` (não mais `mark('failed')`) + `recover_stale_processing` no ciclo | `supabase/functions/worker-dispatcher/index.ts` |
| Test harness (RPC transitions) | `tests/d8/harness/am04_{setup,test,run}.ps1` / `.sql` |

**Sem alteração no cálculo D7/comissão.** `SupabaseOutbox.markFailed` (dominio) continua intacto; o RPC **espelha** a mesma semântica (1 fonte de behavior) — `attempts = retry_attempts+1`; `>= max (5)` → `dead_letter`; senão `pending` com `retry_next_retry_at = now + base_delay_ms*2^(attempts-1)`.
