# 6.1.4 — SMG: Automação de Aprovação Controlada de PR

> **Frente:** Automação do passo "review executor automatizado" da cadeia de merge sobre `main`
> **Data:** 2026-09-11 · **Autor:** OpenCode (Tech Lead operacional)
> **Status:** 🟡 IMPLEMENTADO — aguardando merge autorizado do PO + revisão
> **Autorização:** PO (2026-09-11, verbatim): *"autorizado"* — frente separada com escopo fechado
> **Terminologia oficial:** a conta `review-bot-smg` atua como **"review executor automatizado"** — executa a decisão do PO, **não** é um "reviewer independente" nem decision maker

---

## 1. Objetivo

Automatizar a **execução formal da aprovação** (`APPROVE`) em pull requests de `main` quando, e **somente quando**, o PO emitir o comando explícito `/approve` em comentário no PR.

**A automação NÃO decide nada.** O único agente decisor é o PO. A conta executor (`review-bot-smg`) satisfaz o requisito técnico do branch protection (1 approving review) **executando** a decisão do PO — nada além disso.

### O que a automação NÃO faz (escopo fechado — proibido)

| Proibido | Motivo |
|---|---|
| **Auto-merge** | Decisão do PO: *"Eu não colocaria o merge automático nessa primeira versão"* — aprovação ≠ autorização de merge |
| **Deploy** | Deploy continua sendo gate separado (aprovação explícita do PO) |
| **Alteração de branch protection** | `main` permanece com configuração atual; nenhum `enforce_admins` off, `--admin`, redução de review count |
| **Aprovar sem comando do PO** | Trava fail-closed: qualquer condição insatisfeita = STOP, sem aprovação |
| **Teste nos PRs reais da frente** | Decisão do PO: não usar PRs #35/#36 como cobaia — teste em PR controlado após a implementação |

## 2. Fluxo operacional

```
PO comenta "/approve" no PR
        │
        ▼
workflow smg-pr-approve (issue_comment [created])
        │
        ▼
run.mjs aplica gates fail-closed (sequencial)
        │
        ▼
TODOS os gates PASS → POST /pulls/{n}/reviews {event: "APPROVE"}
        │
        ▼
QUALQUER gate FAIL  → exit 1 (STOP) — nenhuma aprovação
```

### Cadeia de merge completa (contexto)

```
PO autoriza merge  →  review executor aprova (automação /approve, ou manual)
  →  smg-merge (execução do merge pelo OpenCode)  →  verificação pós-merge
  →  novo STOP (documentação + novo ciclo)
```

A automação substitui **apenas** o passo manual da aprovação. Merge e deploy continuam exigindo autorização explícita do PO em cada ocorrência — não há autorização implícita nem persistente.

## 3. Gates fail-closed (ordem de avaliação em `guards.mjs`)

| # | Gate | Condição de PASS | Condição de STOP (fail-closed) |
|---|---|---|---|
| G0 | Comentário em PR | `issue.pull_request != null` | Não é comentário em PR |
| G1 | Autoridade | autor do comentário == `augustosanchesmanager-ux` (PO) | qualquer outro autor |
| G2 | Comando | body (trim) == `/approve` | qualquer outro texto |
| G3 | Estado do PR | `state == "open"` | fechado/merged |
| G4 | Draft | `draft == false` | PR em draft |
| G5 | Base ref | `base.ref == "main"` | qualquer outra base |
| G6 | CI obrigatório | **todas** as check runs `completed` + conclusão verde (`success`/`neutral`/`skipped`) | check pendente OU falha mandatória |
| G6a | Exceção de baseline | `lint advisory` (allowlist explícita) pode estar vermelho — baseline pré-existente documentada (ROADMAP 8.50: 33 erros/213 warnings, continue-on-error) | — |
| G7 | Idempotência | nenhum review `APPROVED` existente | já existe aprovação → nada a fazer (STOP silencioso, exit 0 sem POST) |

**Regra do PO (verbatim):** *"A Action deve falhar fechada se qualquer condição não for satisfeita."* → `run.mjs` sai com exit 1 em qualquer gate FAIL e o job do workflow fica vermelho.

## 4. Segredos e identidade

### `REVIEW_BOT_TOKEN` (secret do repositório, nível Actions)

- **Criado diretamente pelo PO no GitHub** (`Settings → Secrets and variables → Actions`).
- **Nunca é compartilhado com o OpenCode/agente** (decisão do PO, verbatim: *"Não me passe o PAT aqui"*).
- Tipo: **fine-grained PAT** da conta `review-bot-smg`.
- Escopo **mínimo** (decisão do PO):
  - Repositório: `sou-manager` (apenas)
  - Permission: **`Pull requests: Write`** — nada além
- O workflow injeta o valor como `SMG_TOKEN` no step; `run.mjs` nunca loga o token.

### Por que a conta `review-bot-smg` é tipo `User` e não `Bot`

Contas `Bot`/`github-actions[bot]` têm aprovações **ignoradas** pelo branch protection desde 2020 (GitHub ignora "actions bot" approvals). Por isso o executor é uma conta tipo `User` (criada pelo PO) cujo PAT registra review `APPROVED` **válida** para o requisito de branch protection — é a única forma de automação de aprovação compatível com `required number of approving reviews`.

### Precedência da decisão

A aprovação do executor é **execução**, não opinião: o corpo do review deixa explícito:

> "Aprovação automatizada: execução formal do comando /approve autorizado pelo PO. review executor automatizado (não é decisão autônoma). Merge/deploy permanecem gates separados."

## 5. Arquivos da frente

| Arquivo | Papel |
|---|---|
| `.github/workflows/smg-approve.yml` | Gatilho `issue_comment[created]` com pré-filtro; injeta `REVIEW_BOT_TOKEN`; roda `run.mjs` |
| `scripts/smg-pr-approve/guards.mjs` | Gates puras e testáveis (G0–G7), `PO_ACCOUNT`, `ADVISORY_CHECK_NAMES` |
| `scripts/smg-pr-approve/run.mjs` | Executor: lê `GITHUB_EVENT_PATH`, consulta API GitHub, aplica gates, POST APPROVE |
| `scripts/smg-pr-approve/guards.test.mjs` | Suite vitest (22 testes) cobrindo todos os caminhos fail-closed |

### Decisões de implementação

- **Node 22 nativo** (`fetch` global) — zero dependência nova; somente `node:fs` para ler o payload do evento.
- **API GitHub versionada** (`X-GitHub-Api-Version: 2022-11-28`), sem usar `GITHUB_TOKEN` do runner para aprovar (princípio do menor privilégio — o job só lê `contents: read`).
- **Fail-closed com logs**: cada decisão de STOP loga o motivo exato (ex.: `CI com falha mandatória: build=failure`).
- **Idempotência**: se já existe `APPROVED`, o executor encerra sem POST (exit 0, nada a fazer) — nunca duplica aprovação.
- Check runs avaliados pelo **head SHA** do PR (`GET /commits/{sha}/check-runs`) com `per_page=100`.

## 6. Plano de teste (após merge da frente)

1. Criar **PR controlado de teste** (branch efêmera de documentação) para `main`, com CI verde.
2. Comentar `/approve` **como conta que NÃO é o PO** → esperar job vermelho (STOP, sem review).
3. Comentar `/approve` como o PO **em PR draft** → esperar STOP.
4. Simular CI vermelho (PR controlado com falha intencional em doc/validação) + `/approve` → esperar STOP.
5. Comentar `/approve` como o PO em PR aberto/base `main`/não-draft/CI verde → esperar `APPROVED` como `review-bot-smg`.
6. Comentar `/approve` novamente no mesmo PR → esperar idempotência (sem novo review).
7. **NUNCA usar PRs #35/#36** (decisão do PO).

---

## 7. Relação com a governança existente

- Subsiste a regra do branch protection de `main` (1 approving review) — agora executável de forma automatizada apenas sob comando do PO.
- O veredito de merge continua **humano**: após o `APPROVED`, o OpenCode executa `smg-merge` **somente** com autorização explícita do PO para aquele merge específico.
- A `review-bot-smg` **não** substitui o papel de revisão técnica — apenas desbloqueia a proteção mecânica após decisão do PO; a revisão técnica formal permanece responsabilidade do OpenCode/PO nos gates de cada frente.
- Aditivo documental à cadeia registrada em ROADMAP 8.52/7.13 (branch protection preservada, desbloqueio via reviewer) — a automação é a implementação operacional desse fluxo sob comando explícito.
